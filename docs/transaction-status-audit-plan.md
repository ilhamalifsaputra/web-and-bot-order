# Transaction status audit and implementation plan — 2026-10-08

Source: `C:/Users/ilham/Downloads/prompt-scalable-transaction-status-spinner-progress-wallet-topup.md`.

## Audit completed before implementation

1. Transaction storage uses `Order.kind = PRODUCT | WALLET_TOPUP`. Products route to STOCK, MANUAL, or DIGIFLAZZ; catalog groups distinguish GAME_TOPUP and PREMIUM_APPS.
2. Rails are TokoPay, PayDisini, NOWPayments, Bybit internal, Bybit BSC, and Binance internal. `packages/core/src/payments/paymentStatus.ts` already centralizes provider status mapping.
3. IDR paid aliases are paid/success/completed/settlement/lunas/berhasil. NOWPayments settles only finished. Bybit internal success is numeric 2; Bybit BSC success is numeric 3. Binance has no status and requires authenticated transfer matching. Intermediate evidence must never be invented for IDR rails.
4. Payment facts currently live on Order timestamps, Payment attempts, and processed-provider ledgers. Settlement validates authentic provider data, ownership, amount, and currency before domain mutations. Failed domain transactions can roll back payment facts: an explicit persisted payment projection is needed for review.
5. Telegram has payment anchors (`paymentMsgChatId`, `paymentMsgId`) and a separate durable `FulfillmentMessage` worker. Normal flows may therefore produce both a paid bubble and a progress bubble. Wallet completion additionally sends an outbox DM.
6. The worker animates every 2000 ms and reads database state; it makes no provider calls. Leases, unknown-send handling, flood-control backoff, and final-state correction already exist. Its spinner characters have encoding corruption, and no phase percentage is rendered.
7. Canonical customer references are `Order.orderCode`, generated by the existing `uniqueOrderCode`. No new generator is needed.
8. Wallet receipt source of truth is also `Order.orderCode`: `createWalletTopupOrder`, wallet history, pay API, and wallet-credit notifications use it. It must remain full, HTML escaped in Telegram and wrapped in the website.
9. `settleWalletTopup` uses an atomic status claim, `adjustWallet`, a unique wallet movement, and double-entry posting in the settlement transaction. Replayed events do not credit twice. Keep that mechanism intact.
10. Digiflazz stores QUEUED/SUBMITTING/PROCESSING/review evidence separately using dispatchedAt/attempts/status; final callbacks wake the persisted message. Supplier retries are independent of spinner ticks.
11. Premium STOCK delivery can complete synchronously; MANUAL queues await admin and must be static. Credential delivery remains a separate private artifact, not another progress notification.
12. Existing underpaid deliver-anyway uses stock approval, stamps paidAt, and lacks a required reason. It needs explicit ADMIN_OVERRIDE metadata while retaining UNDERPAID payment facts. Wallet exceptions must use existing ledger services.
13. Main risks: concurrent spinner/final writes, menu reuse overwriting another order, photo versus text anchors, legacy notification duplicates, payment rollback losing confirmed facts, partial NOWPayments being treated as failure, and admin override being represented as paid.
14. Frontend boundary rules forbid importing core into the SPA. Backend must send canonical presentation so the client only renders it. Current payState collapses UNDERPAID to closed and displays a spinner for manual processing.

## Selected architecture

Extend the existing Order/Payment and FulfillmentMessage architecture. Nullable paymentState and walletCreditState preserve legacy compatibility; ADMIN_OVERRIDE fields record actor, time, and reason. Use one pure presentation projection in core, transported by backend APIs. Percentages are PAYMENT_DETECTED 25, VERIFYING 35, PAID 40, QUEUED 55, SUBMITTING 65, PROCESSING/CREDITING 80, SUCCESS/CREDITED 100. Waiting, underpaid, manual waiting, review, failed and expired hide progress and stop animation. Completion of manual fulfillment has no progress bar.

Bot order creation reserves a `WAITING_SCREEN` coordinator row before provider or Telegram I/O. Acknowledgement adopts the actual payment message ID using a lease-aware compare-and-set; a unique `(chatId, messageId)` index prevents sharing a bubble across orders. The durable worker edits that same text or QR caption through settlement and fulfillment. Legacy direct writers defer when a coordinator exists. Unknown sends are not blindly retried. Menus open another message when their anchor belongs to a transaction; cancellation, expiry and Buy Again preserve the receipt. Wallet-funded checkout also adopts its checkout message and uses the coordinator for completion.

Payment facts remain committed if wallet credit fails: `paymentState = PAID`, `walletCreditState = NEEDS_REVIEW`, with an actionable deduplicated admin alert. These orders leave automatic payment polling and cannot expire or be cancelled as unpaid. A late authenticated payment received after cancellation still projects a static review warning if credit fails. Actual refund or ledger recovery remains a resolved outcome. Wallet credit retains the existing atomic status claim and unique ledger posting.

## Requested database application and master release

On 2026-10-08 the user requested migration before the local/remote master push. The configured database resolves to local PostgreSQL `bot_order`, schema `public`, on port 5432. Before applying changes, a database-to-schema diff contained exactly the six new nullable columns and Telegram ownership index, with no destructive changes. A preflight found no duplicate non-null `(chat_id, message_id)` pairs.

`node node_modules/prisma/build/index.js db push --skip-generate` stopped at Prisma's generic unique-constraint warning without applying changes. The reviewed additive SQL was applied directly, following the repository's documented SQL alternative, rather than passing `--accept-data-loss`:

```powershell
node node_modules/prisma/build/index.js db execute --schema prisma/schema.prisma --file prisma/migrations/20261008090000_transaction_payment_credit_state/migration.sql
node node_modules/prisma/build/index.js generate
node node_modules/prisma/build/index.js migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --exit-code
```

All three commands passed. Post-application reads confirmed all six columns and the unique index; order, wallet transaction and coordinator row counts were unchanged (all were zero in this local database). The final live-schema diff reported `No difference detected`.

This repository uses `db push`/explicit SQL, so `_prisma_migrations` is not the deployment record. For another environment that does not yet have these columns/index, apply this SQL before starting the new version; the normal Docker `db push` can otherwise stop at its unique-index warning. The production host was not accessed in this release.

The release review found and fixed two additional compatibility issues. Coordinator registration now resolves the legacy Digiflazz provider from the existing catalog fallback while honoring explicit provider snapshots. Storefront SSE now uses the same `unfulfilled_credit` ledger evidence as order detail/list responses, so an actual wallet recovery stays `CREDITED` instead of being overwritten by `CANCELLED`. Both fixes have regression coverage that failed before the changes and passed afterward.

Existing rail tests now acknowledge the real reserved coordinator, then run the durable worker to verify the original message ID/caption, full reference, actual balance, retry state and exactly-once credit. Legacy tests explicitly remove the reservation when testing pre-coordinator recovery. Authenticated short payments assert `UNDERPAID`; the dispatch guard documents the audited underpaid override that intentionally does not auto-dispatch Digiflazz. Security log-capture tests temporarily enable trace output and restore the logger afterward, so assertions remain meaningful even when the test process uses `LOG_LEVEL=error`.

The final release check runs the repository suite with four workers, then rechecks every initially failed file in full after these fixes with two workers and a 120-second integration-test budget. The timeout is a command-line setting for this verification; repository timeout configuration is unchanged. Two unmodified suites (storage API filesystem traversal and concurrent unique-cent allocation) exceeded the original 20-second budget under load and are included in this recheck.
