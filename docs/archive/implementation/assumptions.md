## ASSUMPTION 1 — Mobile navigation: adopt the fixed bottom tab bar

| Field | Value |
|---|---|
| **Date** | 2026-09-02 |
| **Question** | The design system (`foundations.md` §7, `components.md` "Bottom navigation (mobile)", `tokens.json` `layout.bottomNavHeight`) specifies a **fixed bottom tab bar** for mobile primary navigation. The app currently uses a **hamburger + slide-in left drawer** (`apps/storefront/client/src/components/Layout.tsx`). Audit §F escalation #1 flagged that adopting the bottom bar changes the core navigation model on every mobile page, that none of the reference's five tabs (`Home · Transaksi · Promo · Bantuan · Akun`) map cleanly onto this shop's IA, and that a fixed bottom bar would **collide** with the existing sticky purchase / checkout bars on product-detail, cart, checkout, pay, and wallet-top-up screens (two fixed bottom elements on one screen). Which navigation model ships, and — if the bottom bar — which 4–5 destinations get permanent billing? |
| **Decision** | **Adopt the design system's fixed bottom tab bar** as mobile primary navigation — it is the visual authority per prompt §2 KEEP ("navigation patterns"). Adapt composition, not invention (prompt §3.2 rule 3): **(a)** the bottom tab bar is **hidden** on the six full-funnel screens that already dock a sticky action bar at the bottom edge — `/p/:slug`, `/cart`, `/checkout`, `/checkout/:code/pay`, `/wallet/topup`, `/wallet/topup/:code/pay` — so the two fixed bottom elements never coexist; **(b)** five tabs mapped to this shop's real destinations: **Beranda** (`/`), **Cari** (search overlay), **Keranjang** (`/cart`, count badge from `ctx.cart_count`), **Pesanan** (`/account/orders` when signed in, else `/track`), **Akun** (`/account` or `/login`). The reference's "Promo" is dropped (this shop's flash sale is conditional on `ctx.flash_active` — a permanent tab to a possibly-empty shelf is worse than none) and "Bantuan" is dropped from the bar (support is auth-gated here; Cart earns the slot instead); both remain reachable from the retained left drawer, which becomes secondary "more" navigation (Categories, Products, Flash sale when active, language, Help, trust footer). **(c)** `layout.bottomNavHeight` (56px) is now used, with `env(safe-area-inset-bottom)` padding below the bar and matching bottom scroll-padding on the page so content clears it; active item tinted `--pine`. Full spec: `gogogo-frontend/design-system/business-adaptation.md` → Navigation → "Mobile navigation behavior". |
| **Risk level** | **Medium.** Changes the mobile navigation model app-wide (reachability, reserved bottom space) — but reversible: it is a layout/composition change, not a business-logic or data change. No route, endpoint, auth rule, or terminology meaning changes. The drawer is kept, so no destination becomes unreachable. |
| **What changes if wrong** | If the user vetoes the bottom bar → revert to the drawer-only model; the `layout.bottomNavHeight` token goes back to unused (as noted in audit §D1); no other work is invalidated. If the user keeps the bar but wants different tabs → swap tab entries in one layout component; the hide-on-funnel-screens rule (a) and the safe-area handling (c) are independent of the tab choice and stay. If the pre-declared `/search` → overlay deviation does **not** land and the persistent mobile header search field is kept → **drop the "Cari" tab** and ship a 4-tab bar (Beranda · Keranjang · Pesanan · Akun); nothing else changes. If a genuine collision is found on a screen not in list (a), add it to the hidden-on list — the rule generalises. |

## ASSUMPTION 2 — Form library: keep the existing manual-validation convention

| Field | Value |
|---|---|
| **Date** | 2026-09-02 |
| **Question** | Prompt §11 says forms must use "the repository's existing form and validation library, schema-driven." Audit §A / §E / §F escalation #2 established that this repository has **no** schema-driven form library — no `react-hook-form`, `zod`, `yup`, or equivalent in `apps/storefront/client/package.json` or source. Every form (Login, Register, Forgot, Reset, Checkout guest-email + delivery-info step, Settings, WalletTopup amount, Reviews, Support/Ticket composer) uses **controlled React state + native HTML5 validation attributes** (`required`, `minLength`, `maxLength`, `pattern`) **plus hand-written TypeScript validators** in `apps/storefront/client/src/lib/deliveryFields.ts` (`fieldError`, `isValidEmail`) that mirror the server's `packages/core/src/deliveryFields.ts` rule-for-rule; the server is always the real authority. Reading (a): treat that convention as "the repository's existing library" and keep it. Reading (b): introduce `react-hook-form` + `zod` for the Integration phase. Reading (b) is a **new dependency**, which Global Constraints / prompt §15 prohibit unless a task explicitly calls for one. |
| **Decision** | **Keep the existing manual-validation convention.** It **is** "the repository's existing form and validation library" for prompt §11 purposes: controlled state + native HTML validation + centralized hand-written TS validators (`src/lib/deliveryFields.ts`) mirrored server-side. No form library is added. Prompt §11's other form requirements still apply and are implemented on top of this convention: validate on blur, re-validate on change after first error, block submit while invalid, show a pending state during submission, map server errors to field level with a form-level `Alert` fallback, and source validation messages from a **shared message map** (i18n keys) rather than inline strings. New forms follow the same pattern; new shared validators go in `src/lib/deliveryFields.ts` (or a sibling in `src/lib/`), never inline. |
| **Risk level** | **Low.** Reversible — validators are already centralized in one module mirroring the server, so a schema library (`zod` etc.) could be layered in later by wrapping those rules, without UI rework. No new dependency is taken on. Server-side re-validation is unconditional, so client validation being "only" manual is a UX concern, not a correctness one. |
| **What changes if wrong** | If a later task is *explicitly* scoped to add a schema-driven form library: add `react-hook-form` + `zod` (or the then-current choice), port the `deliveryFields.ts` rules into schemas (they are already declarative enough to translate directly), and register the dependency addition as a deviation (§29). Forms would move to `useForm` + resolver, but field-level error display, the shared message map, and server-error mapping — all already required above — carry over unchanged. No business logic, endpoint, or validation *rule* changes; the server contract is untouched. |
